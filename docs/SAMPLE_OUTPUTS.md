# Sample Outputs

This document explains the sample output files generated by the ENMA-WG MEP quantity takeoff PoC.

The purpose of these outputs is not simply to export IFC data to CSV.

They demonstrate how IFC data can be interpreted and transformed into engineering information that can be used for quantity takeoff.

The basic concept is:

```text
IFC Data
   ↓
Relationships / Context
   ↓
Engineering Meaning
   ↓
Engineering Quantity
```

The current PoC focuses primarily on pipe segments and pipe fittings.

---

## 1. Overview

The following four output files represent the core sample results of the current PoC.

| Output file | Description | Data rows |
|---|---|---:|
| `output/pipes_detail.csv` | Engineering attributes extracted and interpreted for individual pipe segments | 252 |
| `output/pipes_summary.csv` | Aggregated pipe quantities | 138 |
| `output/pipe_fittings_detail.csv` | Engineering attributes and connection information for individual pipe fittings | 81 |
| `output/pipe_fittings_summary.csv` | Aggregated pipe fitting quantities | 48 |

Together, these files show the transition from individual IFC elements to engineering quantity information.

# 2. Pipe Elements

## `output/pipes_detail.csv`

This file contains one row for each `IfcPipeSegment` processed by the PoC.

The current source model contains:

```text
IfcPipeSegment : 252
```

Representative columns include:

| Column | Meaning |
|---|---|
| `GlobalId` | IFC GlobalId |
| `Name` | IFC element name |
| `階` | Building storey |
| `配管種別` | Pipe type |
| `系統コード` | System code |
| `系統名称` | System name |
| `IFC系統分類` | IFC system classification |
| `外径` | Outside diameter |
| `内径` | Inside diameter |
| `長さ` | Pipe length |
| `方向区分` | Direction classification |
| `軸DX`, `軸DY`, `軸DZ` | Pipe axis vector |
| `水平面角度_deg` | Horizontal-plane angle |
| `勾配` | Slope |
| `Z最低`, `Z最高` | Minimum and maximum Z coordinates |
| `高低差` | Elevation difference |

The important point is that the file contains more than a direct export of IFC properties.

Geometric information is interpreted to determine engineering attributes such as pipe direction.

For example:

```text
IFC geometry
     ↓
Pipe axis vector
     ↓
Direction interpretation
     ↓
Horizontal / Vertical / Sloped
```

This interpretation allows the IFC elements to be grouped in ways that are meaningful for quantity takeoff.

# 3. Pipe Quantity Summary

## `output/pipes_summary.csv`

This file aggregates the 252 individual pipe elements in `pipes_detail.csv`.

The aggregation dimensions currently include:

- building storey
- system
- IFC system classification
- outside diameter
- direction classification

Representative columns are:

| Column | Meaning |
|---|---|
| `階` | Building storey |
| `系統コード` | System code |
| `系統名称` | System name |
| `IFC系統分類` | IFC system classification |
| `外径_mm` | Outside diameter in millimetres |
| `方向区分` | Direction classification |
| `本数` | Number of pipe segments |
| `長さ_m` | Total pipe length in metres |

The current PoC produces:

```text
Pipe segments : 252
Summary rows  : 138
Skipped       : 0

Total length      : 649.090 m
Horizontal length : 375.963 m
Vertical length   : 273.127 m
Sloped length     : 0.000 m
```

This can be viewed as the following transformation:

```text
252 IFC pipe elements
        ↓
Engineering attributes
        ↓
Grouping / Aggregation
        ↓
138 quantity summary rows
```

The result demonstrates that IFC elements can be converted into structured quantity information while retaining the engineering attributes used for aggregation.

The value `649.090 m` represents the current IFC-based pipe length interpretation used by this PoC. It should not be interpreted as a complete construction estimate.

See [REPRODUCE_PIPE_RESULTS.md](REPRODUCE_PIPE_RESULTS.md) for the detailed reproduction procedure and current limitations.

# 4. Pipe Fittings

## `output/pipe_fittings_detail.csv`

This file contains one row for each `IfcPipeFitting` processed by the current PoC.

The source model contains:

```text
IfcPipeFitting : 81
```

Representative columns include:

| Column | Meaning |
|---|---|
| `GlobalId` | IFC GlobalId |
| `Name` | IFC element name |
| `ObjectType` | IFC ObjectType |
| `PredefinedType` | IFC PredefinedType |
| `TypeName` | IFC type name |
| `継手種類` | Interpreted fitting type |
| `階` | Building storey |
| `系統コード` | System code |
| `系統名称` | System name |
| `IFC系統分類` | IFC system classification |
| `Material` | Material information |
| `PortCount` | Number of ports |
| `接続径1_mm` | Connection diameter 1 |
| `接続径2_mm` | Connection diameter 2 |
| `接続径3_mm` | Connection diameter 3 |
| `径情報完全性` | Completeness of diameter information |
| `径取得元` | Source used to determine diameter |
| `数量_個` | Quantity |
| `Warning` | Missing or ambiguous information requiring attention |

This output illustrates an important ENMA concept:

> Engineering meaning does not always exist as a single property on the IFC element itself.

For some fittings, connection diameter information is obtained by following IFC relationships to connected pipe segments.

For example:

```text
IfcPipeFitting
       ↓
IfcDistributionPort / Connections
       ↓
Connected IfcPipeSegment
       ↓
Pset_PipeSegmentTypeCommon.OuterDiameter
       ↓
Fitting connection diameter
```

In the current output, this can appear in `径取得元` as:

```text
Connected IfcPipeSegment.Pset_PipeSegmentTypeCommon.OuterDiameter
```

This is different from simply reading a property from the fitting itself.

The engineering information is derived from the **relationship and context** of the IFC elements.

That is one of the central ideas behind the ENMA approach.

# 6. What These Outputs Demonstrate

The sample outputs illustrate several principles of the ENMA-WG approach.

## 6.1 IFC is the starting point, not the final quantity

IFC provides geometry, properties, classifications, spatial relationships, systems, ports, and connectivity.

However, construction quantity takeoff requires these data to be interpreted from an engineering perspective.

```text
IFC Data
   ↓
Engineering Interpretation
   ↓
Quantity Information
```

---

## 6.2 Relationships can provide engineering meaning

Engineering information may come from relationships between IFC elements rather than from a single property.

The pipe fitting example demonstrates this clearly:

```text
Fitting
   ↓
Port / Connection
   ↓
Connected Pipe
   ↓
Pipe Diameter
   ↓
Fitting Connection Diameter
```

This type of relationship-based interpretation becomes increasingly important when working with real-world IFC models.

---

## 6.3 Detail and summary should remain traceable

Quantity summaries should not become disconnected from their source IFC elements.

The PoC therefore separates:

```text
Element-level interpretation
        ↓
Quantity aggregation
```

while retaining `GlobalId` and other engineering attributes in the detail output.

This provides a foundation for tracing a quantity result back to the IFC model.

---

## 6.4 Missing information should remain visible

Real IFC models do not always contain all information required for quantity takeoff.

The PoC does not assume that every missing value can be safely inferred.

Fields such as:

```text
径情報完全性
径取得元
Warning
```

are retained so that missing, inferred, or ambiguous information can remain visible.

This concept connects directly to the ENMA data model's human-in-the-loop approach:

```text
Machine interpretation
        ↓
Uncertain / missing information
        ↓
Engineer review
        ↓
Confirmed engineering meaning
        ↓
Quantity result
```

See [DATA_MODEL.md](DATA_MODEL.md) for the broader ENMA quantity takeoff data model.

# 7. Current Limitations

The current sample outputs demonstrate a PoC and should not be interpreted as a complete construction estimate.

Several engineering issues remain outside the current demonstrated scope or require further development, including:

- fitting length and its treatment in pipe quantity calculations
- construction location
- exposed / concealed conditions
- pipe material interpretation
- insulation requirements
- painting requirements
- project-specific specifications
- labor productivity
- treatment of incomplete IFC information
- formal human review workflows
- additional duct quantity takeoff
- equipment quantity and specification interpretation

These are not simply additional CSV columns.

They require engineering rules, reference data, project specifications, inference, and in some cases human judgment.

This is why the ENMA approach separates IFC data from engineering masters, specifications, rules, inference, review, and final quantity results.

# 8. From Sample Output to the ENMA Data Model

The current PoC output files can be viewed as an early implementation of the broader ENMA concept:

```text
IFC Data
   │
   ▼
Element-level information
   │
   ▼
Relationships / Context
   │
   ▼
Engineering Meaning
   │
   ▼
Quantity Results
```

The ENMA data model extends this concept by explicitly separating:

```text
P  Project / Transaction
S  Specification
M  Master
R  Rule
I  Inference / Evaluation
O  Output / Result
```

This makes it possible to ask not only:

> What is the quantity?

but also:

> How was that quantity derived?

That distinction is important for engineering quantity takeoff.

A quantity is not simply read from IFC.

It is produced through an explicit and traceable interpretation process.
